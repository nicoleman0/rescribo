# matching-evaluation Specification

## Purpose

Decides with labelled data whether match suggestions are good enough to show, and reports retrieval and ranking quality separately.

## Requirements

### Requirement: Versioned labelled dataset
The repository SHALL hold a versioned labelled dataset split into development and held-out cases. It covers genuine matches, no-match reports, paraphrases, negation, similar wording with different causes, missing context, misleading version details, and realistic lengths. Synthetic and redacted real data stay distinct.

#### Scenario: Case counts
- **WHEN** the evaluation report is generated
- **THEN** case counts and class balance are derived from the fixtures, not hard-coded

### Requirement: Gates declared before held-out results
Precision, coverage, and minimum sample size gates SHALL be recorded before held-out results are inspected. Zero invalid references, zero cross-workspace references, and deterministic replay are always required.

#### Scenario: Tuning
- **WHEN** weights or thresholds are tuned
- **THEN** only development cases are used, and the configuration is frozen before held-out evaluation

### Requirement: Labels by construction
Synthetic cases SHALL be generated from a known problem, or as a deliberate no-match, so each case carries its expected answer when created. Each case SHALL record its batch, generator model, and whether it is practice (development) or exam (held-out).

#### Scenario: Paraphrase batch
- **WHEN** a generator writes five reports about one problem in different words
- **THEN** each report's expected answer is that problem without separate labelling

### Requirement: Spot-check of each batch
A reviewer SHALL check a random sample of every generated batch before it is used. The reviewer is a person or a reviewer model that is not the tuning agent's model, an evaluation baseline, or the batch's generator. Each verdict SHALL record its reviewer, and a model's verdict its reason. A batch whose sample contains a wrong expected answer MUST be fixed and resampled, or regenerated. Sample size is set with the gates.

#### Scenario: Wrong answer found in sample
- **WHEN** the reviewer marks a sampled case's expected answer as wrong
- **THEN** the batch is not used until it is regenerated and passes a new sample

#### Scenario: Model review
- **WHEN** a reviewer model checks a sample
- **THEN** each verdict names the model and its reason, and a model that generated the batch is refused

### Requirement: Independent generator model
Cases SHALL be generated by a different model from the one that tunes the matcher and from any model used as an evaluation baseline. The generator model SHALL be recorded per batch.

#### Scenario: Batch provenance
- **WHEN** a reviewer opens a batch
- **THEN** it names the model that generated it

### Requirement: Exam cases not used for tuning
Exam cases SHALL stay in the repository but MUST NOT be used to choose features, weights, or thresholds. The exam runs once per frozen configuration.

#### Scenario: Agent tuning
- **WHEN** an agent tunes the matcher
- **THEN** it reads and scores practice cases only

### Requirement: Retrieval and ranking reported separately
The evaluation SHALL report candidate recall@10 and gold matches omitted by retrieval separately from ranking. Ranking is compared with PostgreSQL text-search order on the same candidate pool, reporting top-1 precision, top-3 recall, coverage, abstention, false suggestions on no-match cases, and evidence validity.

#### Scenario: Retrieval miss
- **WHEN** a gold match was not retrieved
- **THEN** it counts as a retrieval miss, not a ranking failure

### Requirement: No unsupported quality claims
Results SHALL state sample sizes, test conditions, and limitations. The project MUST NOT claim matching quality if the gates are not met.

#### Scenario: Gates missed
- **WHEN** the held-out result misses a gate
- **THEN** the report says so and suggestions stay disabled

### Requirement: Automatic failure triage
Each failed exam case SHALL be classified automatically as a retrieval miss, ranking miss, false suggestion, or wrong abstention.

#### Scenario: Right problem never retrieved
- **WHEN** the expected problem is absent from the candidate pool
- **THEN** the case is tagged as a retrieval miss before any human review

### Requirement: Spent exams rotate
Once exam results are used to decide what to fix, those cases SHALL be moved to the practice set by hand. A fresh exam batch MUST be generated and spot-checked before the next exam result counts.

#### Scenario: Retest after a fix
- **WHEN** the matcher is changed after reviewing exam failures
- **THEN** the next score comes from a new exam batch, not the reviewed one

### Requirement: Hosted model baseline
The evaluation SHALL also rank each exam case's candidate pool with a pinned hosted decision model and report the same metrics beside Rust and PostgreSQL ordering. The baseline MUST run only in evaluation tooling on synthetic cases, never in the product. Model version, repeat-run agreement, and cost SHALL be recorded.

#### Scenario: Three-way comparison
- **WHEN** the exam runs
- **THEN** the report shows Rust, PostgreSQL ordering, and the hosted baseline on the same candidate pools with the same metrics

#### Scenario: Product matching
- **WHEN** the application runs matching for a report
- **THEN** no hosted model is called
